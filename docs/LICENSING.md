# Licensing

A VRM carries usage terms. Producing a derived model is exactly the kind of use
those terms govern, so **licensing is a first-class pipeline stage**, not a
disclaimer — it runs before any geometry work, and a rejection is a normal,
expected outcome.

## Two sources of truth

1. **The terms embedded in the VRM itself.** Authoritative.
2. **The caller's attestation.** Typically the VRoid Hub conditions-of-use
   object that 3D-Avatar-Chatbot's VRM Manager already stores per installed
   avatar. It can *supply* terms we cannot read.

> An attestation can never overrule an embedded prohibition.

## Decision table

| Embedded | Attested | Outcome |
| --- | --- | --- |
| prohibited | anything | **rejected** — `source_model_modification_not_permitted` |
| any | `modification: disallow` | **rejected** — same code |
| allowed / allowed+redistribution | not disallowed | **allowed** |
| unknown | `modification: allow` | allowed |
| unknown | `userAttestsModificationAllowed: true` | allowed |
| unknown | nothing, `STRICT_LICENSING=true` | **rejected** — `requires_user_license_attestation` |
| unknown | nothing, `STRICT_LICENSING=false` | allowed |

The two rejection codes are deliberately distinct: one is final, the other is a
question the user can answer.

## VRoid Hub conditions of use

Accepted verbatim, in the shape the chatbot already stores:

```json
{
  "avatarUse": "everyone",
  "violentExpression": "disallow",
  "sexualExpression": "disallow",
  "corporateCommercialUse": "disallow",
  "personalCommercialUse": "profit",
  "redistribution": "disallow",
  "modification": "allow",
  "credit": "necessary"
}
```

`modification` is the field that gates the job. `allow` / `everyone` permit,
`disallow` forbids, and `default` / `author` / anything unrecognised stay
**unknown** on purpose — silently reading them as permission would be the
wrong default.

## VRM spec differences

VRM 1.0 states modification rights directly. VRM 0.x does not: the licence name
carries them, and `ND` (NoDerivatives) is the case that must be caught.
The full mapping is in [VRM_COMPATIBILITY.md](VRM_COMPATIBILITY.md#licence-field-mapping).

## What the client should do

```js
try {
    await forge.createLook({ storageKey, prompt });
} catch (error) {
    if (error.modificationForbidden) {
        // Final. Offer a different avatar.
    } else if (error.needsLicenseAttestation) {
        // Ask the user, then retry with attestModificationAllowed: true.
    }
}
```

Call `POST /v1/avatars/inspect` **before** the job to warn the user early
rather than after they have chosen an outfit.

## Redistribution

Modification and redistribution are separate rights. VRoid's common default,
`Redistribution_Prohibited`, means "derive freely for yourself, do not share
it" — which is why modification is permitted for it while redistribution is
recorded as `false`.

`redistribution_allowed()` resolves the effective answer. The pipeline does not
currently block on it, because it never publishes a look beyond the requesting
user; if you add sharing, gate it on that value.

## Derived-model provenance

Every generated VRM records where it came from:

```json
{ "extras": { "wardrobeForge": {
    "lookId": "look_…", "sourceAvatarSha256": "abc123…",
    "generator": "3D-Wardrobe-Forge (native engine)" } } }
```

The source's own metadata — author, licence, permissions — is **carried through
unchanged**. A derived look inherits the original's terms; it does not reset
them.

## This repository's own licence

The code is MIT (see `LICENSE`). The garment templates are original,
procedurally-defined parameters, and the calibration avatars are generated by
`wardrobe/vrm/build.py`. No third-party model is redistributed here — which is
also why the test suite needs no licence exceptions.
